# AtCoder 振り返り

コンテスト後の振り返りを、根拠のあるレビューとして返すためのスキル。

読み手は Ruby で参加している経験者で、目的は「次のコンテストで 1 問多く、あるいは 10 分早く
解けるようになること」にある。だから、解説の要約を並べるのではなく、**本人のコードと本人の
コンテスト中の動きに対して**何が言えるかを書く。全問を同じ厚さで扱わず、伸びしろのある問題に
紙面を使う。

**最初に Skill ツールで `atcoder-ruby` を読み込む。** 振り返りでは本人の Ruby コードの計算量や
書き方に必ず触れることになり、そこで CRuby の事実を間違えると（たとえば `Array#shift` を O(N) と
言うと）レビュー全体の信用がなくなる。このリポジトリの書き方の流儀もそこにまとまっている。

## 手順

### 1. 対象を決める

- コンテスト ID が言われていればそれを使う。言われていなければ、最近更新されたコンテストの
  ディレクトリ（`ls -dt */contest.acc.json | head -5`）から推定し、どれを対象にしたかを冒頭で伝える。
- 「F だけ」「E と F」のように問題を指定されたら、その問題だけを深く見る。結果の表、
  時間の使い方、`review.md` への保存の確認は省く。学び・次にやること・ヘッダー案は残してよい。

### 2. 材料を集める

コンテストのフォルダ（acc が作る `abc478/` など）が並ぶリポジトリのルートで実行する。
スクリプトは cwd から上にたどって `Gemfile` か `.agents` がある場所をルートとみなす。見つからない
構成なら `--root <DIR>` で渡す。以下の `<skill-dir>` は、このスキルのディレクトリ（読み込み時に
Base directory として示される絶対パス）に置き換える。

```bash
python3 <skill-dir>/scripts/atcoder_fetch.py info abc478
```

1 回で次のものが JSON で返る。自分で個別に取りに行かなくてよい。

| キー | 中身 |
|---|---|
| `start` / `end` / `duration_minutes` | 開催時刻 |
| `result` | 順位、`rated`、`old_rating`（参加前のレート）、`performance`、`new_rating` |
| `tasks[].points` / `difficulty` | 配点と、AtCoder Problems の difficulty（コンテスト直後は `null`）。サイトの表示と同じく 400 未満を正の値に補正済みで、補正前の値は `raw_difficulty` |
| `tasks[].local.untouched` | 手元の解答が未着手（テンプレートのまま・空・入力を読んでいない）か |
| `tasks[].local.own_lines` | テンプレート以外の行数 |
| `tasks[].local.modified_minute` / `modified_after_end` | ファイルの最終更新が開始から何分後か、終了後か |
| `tasks[].local.header` / `test_command` | 既存のヘッダータグ、サンプルを流すコマンド |
| `tasks[].submissions` | コンテスト中/後の提出、`accepted_minute`、`wrong_before_ac`（AC 前の不正解数。未 AC なら不正解の総数） |
| `tasks[].editorials` | 問題ごとの解説（`official`、`lang`、`video`、`pdf`、URL） |
| `contest_editorials` | コンテスト全体の解説（古いコンテストは公式解説がここの PDF だけ） |
| `notes` / `errors` | 取れなかった情報とその理由 |

`notes` と `errors` は必ず読む。取れなかった情報は推測で埋めず、振り返りの中で「未取得」と書く。

提出履歴は AtCoder Problems の API から取るが、API が使えないか未反映のとき（コンテスト直後に多い）は、
スクリプトが oj のログインセッションで AtCoder 本体の「自分の提出」を読む。結果が未確定のあいだは、
同じ方法で順位表から暫定の順位を取り、`result.provisional` が true になる（`performance` と
`new_rating` は `null`）。そのときは順位に「暫定」と付ける。どちらで取ったかは `notes` に出る。
oj のセッションが切れていると `errors` に出るので、本人に `oj login https://atcoder.jp/` を頼む。

**AtCoder ID が未設定と出たら、先に本人に ID を聞く。** 順位・AC 時刻・ペナルティは、どの問題を
厚く見るかを決める材料なので、後から届くと分類からやり直しになる。答えをもらったら
`atcoder_fetch.py set-user <ID>` で保存し（次回から聞かずに済む）、`info` を取り直す。
本人に聞けない、または答えが得られないときは、下の「提出履歴がないとき」の方法で進める。

問題文と解説の本文は同じスクリプトで読む。WebFetch は要約を挟むので、数式や実装例の細部が
落ちることがある。解法の比較には原文が必要なので、こちらを使う。

```bash
python3 <skill-dir>/scripts/atcoder_fetch.py task abc478 d
python3 <skill-dir>/scripts/atcoder_fetch.py editorial https://atcoder.jp/contests/abc478/editorial/26537
```

解説は `official: true` かつ `lang: "ja"` で、`video` でも `pdf` でもないものを基本にする。
ユーザ解説は別解を探すときに読む。外部ブログと PDF は WebFetch か Read で読む。動画は読めないので
URL を案内するだけにする。問題文の `[図: URL]` は図があった場所で、必要なら Read で画像を見る。

### 3. 着手した問題は、全問で公式解説を読む

A・B のように見ただけで分かる問題を除き、本人がコードを書いた問題はすべて公式解説を読む。
difficulty が低い問題でも、本人の解法と公式の解法が違うことはよくあり、その違いこそ振り返りの
材料になる。読むのは 1 問 1 リクエストで、キャッシュもされるので惜しまない。

読む順番は次のとおり。

1. **問題文と制約**を読み、自分なら何を使うかを先に考える。
2. **本人のコード**を読み、何をしているか・計算量はいくつかを自分の言葉で言えるようにする。
3. **公式解説**を読み、2 と比べる。
4. 必要なら**ユーザ解説**を読んで別解を拾う。

解説を先に読むと、本人の解法を「解説と違う＝劣っている」と見てしまいやすい。実際には解説より
簡潔だったり、別の典型に落としていたりすることがある。先にコードを自分で理解しておくと、
そこを正しく評価できる。

### 4. 問題ごとに厚さを決める

解説まで読んだうえで、全問を次のどれかに分類する。

| 状態 | 判定 | どれだけ書くか |
|---|---|---|
| 余裕で AC | 不正解なし、difficulty が本人のレートより十分低い、公式と同じ方針 | 2〜3 行。アルゴリズム名と、あれば一言 |
| AC したが公式と方針が違う | 上と同じだが解法が違う | 「公式解説との違い」を中心に書く |
| 手こずって AC | 不正解あり、または前後の問題に比べて時間がかかっている | 何で詰まったかを特定して書く |
| 着手したが未 AC | 手元にコードがあるが AC していない | **最も厚く**。どこまで合っていて、どこで外れたか |
| 終了後に AC | コンテスト中は通せず、終了後に通した | 厚く。解法は合っているので、何に時間を使ったか、どの観察が出れば間に合ったか |
| 未着手で射程内 | `untouched` で、difficulty がレート + 400 程度まで | 厚く。何に気づけば解けたか |
| 未着手で射程外 | それより上 | アルゴリズム名と解法の骨子を数行。詳細は求められたら |

厚く書くのは、本人が次に解けるようになる可能性が高い問題である。A・B を丁寧に褒めても得るものは
少なく、G の高度典型を長々と説明しても今は届かない。

- **レート**は `result.old_rating` を使う。なければ、コンテスト中に AC した最も難しい問題の
  difficulty を目安にする。difficulty が `null` のときは `points` で代用する。
- **本人の発言は根拠にしてよい。**「E は通した」「F は手も足も出なかった」と言われたら、
  提出履歴がなくてもそのとおりに扱う。
- **`untouched` は目安**である。`false` でも `own_lines` が数行なら、自分で中身を見て判断する。
- **`result.rated` が false** なら「unrated 参加」と書き、パフォーマンスとレート変化は書かない。
- **提出がすべてコンテスト終了後**（バーチャル参加や後日の練習）のときは、AC 時刻とペナルティの
  欄を省き、時間の使い方も論じない。

**提出履歴がないとき**（ID が未設定、または AtCoder Problems に未反映）は、次の 2 つから推定する。

- `modified_minute`: ファイルを最後に保存した時刻。コンテスト中の AC 時刻のおおよその代わりになる。
- `modified_after_end`: true なら、コンテスト後に書いたか書き直したコードである。コンテスト中に
  AC したとは限らないので、「コンテスト後に更新されている。本番で通したかは未確認」と書く。

推定で書いた項目には、表でも本文でも「推定」と付ける。完数や順位を推定で言い切らない。
結果の表は、「結果」を「サンプル通過」、「AC 時刻」を「最終保存（開始から）」、「不正解」を
「未取得」に置き換える。

提出履歴があるときも、手元の `main.rb` が提出したものと同じとは限らない。提出の `length` と
`local.bytes` が大きく違う、提出は WA なのに手元はサンプルを通る、といった食い違いがあれば、
その旨を書いたうえで手元のコードを見る。

### 5. 言う前に確かめる

振り返りの価値は正確さで決まる。間違った指摘は、何も言わないより害が大きい。

- **サンプルを実行する。** `tasks[].local.test_command` をそのまま使う。サンプルが通ることと
  AC は別なので、提出履歴がないときは「サンプルは通過（AC かは未確認）」と書く。
- **バグを指摘するなら反例を作る。** 「この場合に落ちそう」で止めず、小さい入力を実際に流して
  確かめる。怪しいが反例が思いつかないときは、愚直解と入力の生成器を書き、
  `scripts/stress.py` で突き合わせる（最初に食い違った入力を表示する）。
  作業用のファイルはスクラッチパッド（一時ディレクトリ）に置く。

  ```bash
  python3 <skill-dir>/scripts/stress.py \
    --gen 'ruby gen.rb' --sol 'ruby abc478/d/main.rb' --brute 'ruby brute.rb' -n 300
  ```
- **改善案のコードを出すなら動かす。** サンプルを通していないコードを「こう書けます」と出さない。
- **計算量は制約に当てはめて言う。** 「O(N log N) で N = 2×10^5 なので問題なし」のように、
  その問題の数字で書く。
- **本人の `main.rb` は書き換えない。** 改善版を見せたいときは回答の中にコードで示す。
- **テンプレート由来の行は指摘しない。** `main.rb` の先頭にある未使用の `require`、`inside?`、
  `bsearch`、`MOD`、`INF` は acc のテンプレートで、本人がその問題のために書いたものではない。
  「未使用の require があります」は雑音になる。`MOD` の値が問題と食い違って答えが変わる、
  のように結果に影響するときだけ触れる。

Ruby で TLE している場合の扱いには決まりがある。解法のオーダーが悪いなら、それは解法の改善点
として書く。解法が想定解と同じオーダーなのに落ちているなら、「解法は正しいが Ruby では定数倍が
足りない」と事実を伝えて終える。`while` への書き換えやライブラリの手書き展開といった定数倍の
調整は提案せず、自分が書く実装例にも入れない。他言語との速度比較や「それでも Ruby で通せます」
という話もしない。本人の目的は本質的な解法を身につけることで、定数倍の工夫はそこから外れるため。
`atcoder-ruby` には僅差の TLE に `while` を使う話が出てくるが、振り返りではこちらを優先する。

AC した解答の実行時間に触れてよいのは、**オーダーの違う別解があるとき**だけである（O(N log N) の
解に対して O(N) の解がある、など）。それは解法の話なので「別解」に書く。同じオーダーのまま
速くする話は、通っている以上しない。最大入力での実測（`stress.py --input`）は、オーダーの違いを
裏づける数字として添えるぶんにはよいが、手元の計測でありジャッジの結果ではないと明記する。

### 6. 問題ごとに書くこと

**アルゴリズム名**を全問に書く。名前があると、後で検索でき、類題と結びつき、「自分はどの
分野が弱いか」を数えられる。付け方は `references/algorithm-names.md` に従う。要点は次の 3 つ。

- 道具（データ構造・アルゴリズム）と、考察の型（言い換え・典型テクニック）を分けて挙げる。
  例: 道具 =「優先度付きキュー」、型 =「イベントソート」。
- 本人の解法と公式解説で使っているものが違うなら、両方を書く。公式の名前は、公式解説を
  実際に読んで確かめたものだけを書く。
- 定着した名前がない考察は、造語を作らず、やっていることを短く説明して代える。

AC した問題には次を書く（該当がない項目は省く。無理に埋めない）。

- **良いところ** — 具体的に。「きれいです」ではなく、「種類ごとの個数を Hash で持ち、0 に
  なったら消しているので、Hash の大きさがそのまま答えになっている」のように、何がどう効いて
  いるかを書く。良い点が特にないなら書かない。褒めるために褒めると、本当に良い点が埋もれる。
- **改善できるところ** — 優先度の高い順に。(1) 正しさ（たまたま通っているだけの箇所）、
  (2) 計算量、(3) 実装の単純さ・バグの入りにくさ、(4) コンテスト中の速さにつながる書き方。
  好みの範囲の話は、書くとしても最後に一言だけ。
- **公式解説との違い** — 同じなら「公式と同じ方針」で済ませる。違うなら、どちらが何に強いか
  （実装量、計算量、応用の利きやすさ）を比べる。優劣を決めつけない。
- **別解** — 実際に成り立つものだけ。考え方の出発点が違うもの（例: データ構造で処理する解と、
  言い換えで単純にする解）を優先し、それぞれどんなときに選ぶとよいかを添える。
- **不正解の原因** — WA や RE が出ていたら、何が原因だったかを提出結果とコードから推定する。
  過去の提出コードは手元にないことが多いので、断定できなければ候補を挙げて本人に確かめる。

解けなかった問題には次を書く。

- **解法の骨子** — 公式解説を、本人が知っている道具の言葉で言い直す。解説の丸写しにしない。
- **気づきたかったポイント** — 解法全体ではなく、最初の一歩になる観察。「制約のここを見れば
  この方針が候補に上がる」「この操作は○○と同じ」のように、次に似た問題で思い出せる形にする。
- **着手していた場合** — 方針がどこまで合っていたか。あと少しだったのか、根本から違ったのか。
  直せば通るなら、最小の直し方を示す。
- **手持ちの知識との距離** — 知っている典型の組み合わせで届くのか、新しく覚えるものがあるのか。
  新しく覚えるものには名前を付け、何を学べばよいかを書く。本人がその道具を過去に使ったかは、
  リポジトリを検索すれば分かる（`grep -rl "lazy_segtree" --include=main.rb .` のように、
  `require` しているライブラリ名やヘッダーのタグで探す）。見つかったら「`abc417/f` で使った
  遅延セグメント木がそのまま使える」のように、本人の解答を指して書く。

実装例は、求められたら書く。最初から全問の模範解答を並べると、読む量が増え、自分で実装し直す
機会も奪う。書くときは Ruby で、`atcoder-ruby` の流儀に合わせ、サンプルを通してから出す。

「答えは言わないで」「ヒントだけ」と言われたら、未 AC の問題は骨子を伏せ、弱いヒントから順に
1 つずつ出す（方針の分類 → 鍵になる観察 → 解法の骨子）。次を出すかは本人に決めてもらう。

### 7. 全体の振り返り

コンテスト 1 回分を見たときは、問題別の後に全体について書く。

- **時間の使い方** — AC 時刻の間隔を見て、どこで時間を使ったか。時間をかけた問題は、考察・
  実装・デバッグのどこで詰まったと思われるか。提出履歴がなければ、ファイルの更新時刻からの
  推定であることを明記する。
- **今回の学び** — 1〜3 個に絞る。次のコンテストで思い出せる具体的な一文にする
  （「区間の追加・削除は、時刻順のイベントに直すと数えやすい」など）。
- **次にやること** — upsolve するとよい問題（射程内の未 AC を優先）と、復習するとよい分野。
  類題を挙げるときは、実在を確認できた問題だけにする。記憶だけで問題番号を書かない。
- **繰り返している傾向** — 過去の振り返り（`find . -maxdepth 2 -name review.md` で探す）が
  あれば新しいものを 2〜3 件読み、同じ種類のつまずきが続いていれば指摘する。`review.md` が
  まだなくても、直近 2〜3 回の `info` を取れば AC 時刻（なければ保存時刻）の並びは比べられる。
  はっきりした傾向が見えたときだけ、根拠の数字と一緒に書く。

## 出力

日本語で書く。数式は LaTeX を使わず、`A[i] + K - 1` のようにコード記法かプレーンテキストで書く
（ターミナルでは `$...$` が表示されないため）。スクリプトが返す問題文と解説は TeX のままなので、
引用するときは書き直す。

次の形を基本にする。該当がない項目は見出しごと省く。下の例は形を示すための架空のもので、
値や名前を引き写さない。

```markdown
# ABCxxx 振り返り

## 結果
4 完（A〜D） / 2345 位 / パフォーマンス 987 / レート 950 → 962

| 問題 | 配点 | diff | 結果 | AC 時刻 | 不正解 | アルゴリズム |
|---|---|---|---|---|---|---|
| A （問題名） | 100 | -900 | AC | 2 分 | 0 | 算術 |
| D （問題名） | 400 | 800 | AC | 41 分 | 1 | 幅優先探索、状態をグラフの頂点とみなす |
| E （問題名） | 450 | 1200 | 着手・未 AC | - | 2 | 公式: 動的計画法:bit DP |
| F （問題名） | 500 | 1700 | 未着手 | - | - | 公式: 遅延セグメント木 |

## 問題別

### D - （問題名）（diff 800 / AC 41 分 / 不正解 1）
**アルゴリズム**: 幅優先探索、状態をグラフの頂点とみなす（公式も同じ）

**あなたの解法**: 何をしているかを 1〜2 文で。計算量を制約に当てはめて。

**良いところ**
- ...

**改善できるところ**
- ...

**公式解説との違い**: ...
```

## 記録に残す

コンテスト 1 回分の振り返りを出し終えたら、最後に次の 2 つをまとめて 1 回だけ聞く。どちらも
本人のリポジトリにファイルを作る・書き換える操作なので、聞かずに行わない。

- **`<コンテスト>/review.md` に保存するか。** 振り返りを残しておくと、次回以降に「同じ種類の
  つまずきが続いていないか」を見られる。保存するのはターミナルに出したものと同じ内容。
  既に `review.md` があるときは、上書きするか追記するかも聞く。
- **ヘッダーコメントを `main.rb` に書き込むか。** このリポジトリの解答は、先頭に `# -`、問題 ID、
  アルゴリズムのタグを書く形を取る（`atcoder-ruby` の `references/idioms.md` が形式の基準）。
  振り返りで付けた名前をタグにした案を「ヘッダー案」に示す。広い分類から具体的な手法の順に、
  1 行に 1 つ書く。既にヘッダーがある問題と、未着手のファイルは対象にしない。

  ```ruby
  # -
  # ABCxxx/D
  ```

## サブエージェントを使うとき

ユーザーがサブエージェントの使用を認めているときは、厚く見る問題を 1 問ずつ並列に調べてよい。
各エージェントには、問題 ID、`main.rb` のパス、解説の URL、このファイルの手順 3・5・6 を渡し、
「確かめた事実」と「推定」を分けて返させる。結果の表と全体の振り返りは、集めた後に自分で書く。
厚く見る問題が 1〜2 問のときは、分けずに自分で読むほうが速い。

## 参照ファイル

- `references/algorithm-names.md` — アルゴリズム名・典型テクニック名の語彙と付け方。
